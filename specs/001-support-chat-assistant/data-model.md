# Data Model: Caramel AI Support Chat Assistant

All entities are held in backend memory for the MVP (research.md R3). Nothing is persisted.

## Session

| Field | Type | Rules |
|-------|------|-------|
| `id` | UUID | Generated by the server. Returned to the client once. |
| `createdAt` | timestamp | Set on creation. |
| `lastActivityAt` | timestamp | Updated on each message. Session expires 30 minutes after this. |
| `status` | enum: `active`, `escalated`, `expired` | `escalated` after an escalation ticket is created. Sessions stay usable after escalation so the customer can keep asking. |
| `messages` | ordered list of Message | Full list held for display (FR-006). Only the most recent exchanges within the token budget are sent to the model (FR-003). |

**Transitions**: `active` → `escalated` (on ticket creation) · `active`/`escalated` → `expired`
(idle timeout) · any → removed on expiry.

## Message

| Field | Type | Rules |
|-------|------|-------|
| `id` | UUID | Server-generated. |
| `sessionId` | UUID | Must reference an existing session. |
| `role` | enum: `customer`, `assistant` | Set by the server, never by the client. |
| `content` | text | Customer messages: 1 to 4,000 characters, not blank (spec Edge Cases, FR-001). Assistant messages: the streamed answer, complete once `done` is sent. |
| `status` | enum: `complete`, `failed` | `failed` when the provider errored or timed out. The UI shows the error text (FR-008). |
| `createdAt` | timestamp | Set when the message is recorded. |

**Validation**: Empty or whitespace-only customer content is rejected before it is stored.
Content over 4,000 characters is rejected with a "too long" error.

## Feedback

| Field | Type | Rules |
|-------|------|-------|
| `messageId` | UUID | Must reference an assistant message in the same session. |
| `rating` | enum: `up`, `down` | Required. |
| `recordedAt` | timestamp | Updated when the rating changes. |

**Uniqueness**: One feedback record per assistant message. Changing the rating updates the
existing record (spec User Story 5, scenario 2).

**Privacy**: No free text is stored (research.md R8).

## EscalationRequest

| Field | Type | Rules |
|-------|------|-------|
| `id` | UUID | Server-generated. |
| `sessionId` | UUID | Must reference an existing session. |
| `reason` | enum: `customer_request`, `assistant_unable` | Set by the server based on how the escalation was triggered. |
| `ticketRef` | string | Returned by the ticketing system. Shown to the customer. |
| `ticketPayload` | object | Session reference, reason, and the customer's latest message only, until `CHAT_RETENTION_POLICY` is recorded (plan.md, Constitution Check). No full transcript. |
| `status` | enum: `created`, `failed` | `failed` when the ticketing system is unavailable. The customer is told so (FR-008). |
| `createdAt` | timestamp | Set on creation. |

## Relationships

- A Session has many Messages (ordered).
- A Session has many EscalationRequests (usually one, but a customer can escalate again).
- A Feedback belongs to exactly one assistant Message.

## Metrics (derived, SC-006)

Counts and rates only, computed from the entities above without storing personal data:
resolved-without-escalation share (sessions with no EscalationRequest), thumbs-up ratio
(Feedback `up` over total), escalation rate and reasons (EscalationRequest by `reason`), and
median time from customer message to first assistant token.
